Introduction  What makes a project "agentic"? A regular AI script sends one prompt and gets one answer back. An agentic AI project is different:  the AI is given a goal, a set of tools it is allowed to use (like a calculator or a note-saver), and it  decides for itself which tool to use and when. Some agentic systems go further and split the work  across several specialized agents that pass tasks to one another, similar to a small team where each  member has a specific job.

Many real agentic systems also use Retrieval-Augmented Generation, or RAG: before answering, the  agent looks up relevant passages from a knowledge base it's been given, so its answer is grounded in  real material instead of only what the model already happens to know. Both projects in this guide  include a RAG component for exactly this reason. This guide walks through two such projects, each building on the last:  ● Project 1 — StudyBuddy: a single agent that can talk to you, do quick math, save notes, quiz  you, and answer questions by retrieving passages from your own study notes.

● Project 2 — Blog Post Factory: three agents (a researcher, a writer, and an editor) that pass  work to each other, where the researcher grounds its findings in a small library of source  material you provide, using the same RAG approach as Project 1. Why these tools  Both frameworks are free and open source. For the language model itself, this guide uses Google's  free Gemini API tier, since it needs no local hardware and pairs naturally with Google ADK.

If you'd  rather use a different provider, free tiers are also available from places like OpenRouter, Groq, and  GitHub Models — swap the API key and model name and the rest of this guide stays the same. Who this guide is for  You should be comfortable with basic Python — writing a function, running a .py file, and installing a  package with pip. You do not need any prior experience with AI, agents, or RAG; every new idea is  explained the first time it comes up.

How to use this guide  This guide is a specification, not a copy-paste tutorial: each step describes what a piece of code  should do — its inputs, its behavior, its output — rather than handing you the finished code. Working out the implementation yourself is where the real learning happens; lean on the official  docs and samples linked in Additional Resources if you get stuck on the framework-specific parts. Do the shared setup once, then read the RAG section before starting either project, since both reuse  the same retrieval approach.

How Retrieval-Augmented Generation (RAG) Works Here  Both projects ground their answers in material you provide, instead of relying purely on what the  model already knows. That's done with a small, reusable retrieval pipeline that you'll build once and  use in both projects. The pipeline has four setup stages and one stage that runs every time the agent  needs an answer:  ● Gather your source material — a handful of plain text files. Your own class notes for Project  1, or a few saved articles for Project 2. A handful of files with a few paragraphs each is plenty  to test with.

● Chunk it — split each file into smaller pieces, roughly a paragraph or a few hundred words at  a time. Smaller, focused chunks tend to retrieve more precisely than whole documents. ● Embed it — turn each chunk into an embedding: a list of numbers that captures its meaning,  produced by a small, free, local embedding model (no API key or internet needed for this  step). ● Store it — save each chunk's text alongside its embedding in a local Chroma collection, so  this work only needs redoing when you add new source files, not on every run.

● Retrieve (runs on every question) — embed the incoming question or topic the same way,  ask Chroma for the closest few stored chunks, and hand their text to the agent as grounding  for its answer. You'll build the first four stages as a small, one-time ingestion routine, and the fifth as a tool your  agent can call. Project 1 points this pipeline at a library folder of your own notes; Project 2 points the  same pipeline at a sources folder of reference material — if you've already built it once, Project 2 is  mostly reuse.

Project 1 — StudyBuddy (Google ADK)  What you'll build  A command-line and browser-based study assistant. You can ask it questions, hand it a math  problem, ask it to save a note for later, or ask it to quiz you on a topic — and, when a question  touches on material you've given it, it answers by retrieving and grounding itself in your own notes  rather than guessing.

Learning outcomes  ● Setting up and running an agent framework from scratch  ● Specifying custom tools — plain functions an agent can call — by their inputs, behavior, and  outputs  ● Building a simple retrieval pipeline and giving an agent a tool that uses it  ● Writing clear instructions that shape when an agent uses each tool  ● Running an agent two ways: a terminal chat and a local browser UI  Requirements  Finish the shared setup and read the RAG section above.

Beyond that you'll need the ADK library  itself, a way to talk to Gemini (or your chosen alternative), a local embedding library, and a local  vector database — all installable with pip, the same way you'd install any Python package.

How it works  You ask a question  →  does it need my notes? →  if yes, retrieve matching passages   →  StudyBuddy answers, grounded in what it found    Tools you'll build  Tool Input What it should do  calculate An arithmetic expression, e.g.

"12 * 4 + 7" Safely evaluate it and return the numeric result, or a clear error if it contains anything besides numbers and + - * / ( )  save_note A topic and a note Append a line to a local notes file and confirm it was saved  track_quiz_score Whether the last answer was correct Update a running correct/total counter for the session and return the current score as text  search_study_material The student's question  Embed the question, search the vector database  for the closest matching chunks of the student's  own notes, and return their text as context    Step-by-step build guide  Step 1: Get your model access sorted  Make sure your Gemini (or alternative) API key from the shared setup is available to your code as an  environment variable.

Step 2: Set up the agent's package folder  ADK expects each agent to live in its own Python package: a folder containing a small file that  imports the module where the agent is defined, and a second file that actually defines the agent and  its tools. Create that folder structure for StudyBuddy. Step 3: Build your retrieval pipeline  Following the five stages described in the RAG section above, write the ingestion routine pointed at  a library folder, and drop in two or three text files of your own notes to test with. Step 4: Write the four tools  Implement each tool from the table above.

For calculate specifically, reject anything that isn't a  number or a basic operator before evaluating it, so it can't be used to run arbitrary code. Step 5: Define the agent  Register the model and the four tools on the agent, and write instructions that cover: use calculate  for any math; check search_study_material before answering anything that might be covered in the  student's notes, and say so plainly if nothing relevant turns up; use save_note when asked to  remember something; and call track_quiz_score after each quiz answer, sharing the running score.

Step 6: Run the ingestion routine once

Populate the vector database before your first chat. Re-run it whenever you add new files to the  library folder. Step 7: Start the agent  ADK ships with both a local browser-based chat UI and a terminal chat mode — try StudyBuddy in  whichever you prefer.

Running and testing StudyBuddy  Try each of these to exercise every part of the system:  ● "What's 342 times 17?" — should use calculate  ● "Save a note: mitochondria is the powerhouse of the cell" — should use save_note and  create a notes file  ● "Based on my notes, explain the water cycle" — should retrieve and reference your own  material specifically, not just general knowledge  ● "Quiz me on the water cycle" — should ask one question at a time and track your score  Troubleshooting  ● Answers ignore your notes — check the ingestion routine actually ran and the library folder  wasn't empty, and that the agent's instructions explicitly say to check notes before  answering.

● Retrieval returns unrelated passages — your chunks may be too large or too small; try  splitting text into smaller, more focused pieces. ● The first run feels slow — the embedding model downloads once, a small file, the first time  it's used; later runs are fast. ● API errors from the model — double-check your key is set correctly as an environment  variable, and that you haven't hit the free tier's rate limit; space out requests if so. Level up: stretch goals  ● Add PDF support so you can drop in scanned or extracted textbook chapters, not just plain  text notes.

● Have the agent mention which file or topic an answer's grounding came from. ● Automatically re-run ingestion when it notices new files in the library folder. ● Add a "flashcard mode" that turns retrieved passages into quiz questions instead of only  using them for direct answers. Project 2 — Blog Post Factory (Microsoft Agent Framework)  What you'll build  A small pipeline of three cooperating agents.

You give it a topic; a researcher agent retrieves  relevant facts from a library of your own reference material using the same RAG approach as Project  1, a writer agent drafts a short blog post from those facts, and an editor agent polishes the draft  before it's saved to a Markdown file.

Learning outcomes  ● Defining several agents, each with a narrow, specific job  ● Chaining agents together with a sequential multi-agent workflow  ● Reusing a retrieval pipeline you already built, inside a new project  ● Seeing how information flows and changes from one agent to the next  Requirements  Finish the shared setup and RAG section earlier in this guide. This project reuses the same  embedding and vector-database packages as Project 1, plus the multi-agent framework itself, all  installable with pip.

Tech stack  Layer Choice Why  Agent framework Microsoft Agent Framework Open source (MIT), built-in multi-agent orchestration patterns  Language model Google Gemini free tier (or another free-tier provider) Works through Agent Framework's native Gemini connector, or any OpenAI- compatible free provider  Embeddings Same local embedding model as Project 1 Reuse what you already built  Vector database Chroma (same as Project 1) Reuse what you already built  Orchestration SequentialBuilder  Runs researcher, then writer, then  editor, automatically forwarding each  agent's output    How it works  Your topic  →  researcher (retrieves grounded facts via RAG)  →  writer (drafts)  →   editor (polishes)  →  blog_post.md    Each agent only sees the instructions it was given and the conversation passed to it by the workflow  — the researcher never writes prose, and the writer never touches the vector database.

Keeping  each agent's job narrow is what makes multi-agent systems easier to debug than one agent trying to  do everything at once. Agents you'll build  Agent Given Job  researcher The topic, plus a retrieve_from_sources tool Retrieve relevant facts from your saved sources and reply with a short bulleted list, noting which file each fact came from

Agent Given Job  writer The researcher's bulleted facts Draft a short blog post — a title and three to four paragraphs — using only the facts it was given  editor The writer's draft Tighten the language, fix grammar, ensure a clear title, and return only the finished Markdown post    Step-by-step build guide  Step 1: Point your retrieval pipeline at a sources folder  Reuse the ingestion routine from Project 1, this time aimed at a sources folder containing a handful  of saved articles or notes about a topic you want to write about.

Step 2: Write the retrieve_from_sources tool  Same shape as StudyBuddy's search_study_material tool: take a topic, embed it, look up the closest  chunks in Chroma, and return their text along with which source file each came from. Step 3: Define the three agents  Implement researcher, writer, and editor as specified in the table above, giving each clear, narrow  instructions. Step 4: Wire them into a sequential workflow  Hand the three agents to a SequentialBuilder in order.

Running the resulting workflow with a topic  string automatically passes the researcher's output to the writer, and the writer's output to the  editor; the editor's reply is your finished post. Step 5: Save the finished post  Write the editor's final Markdown output to a file so it's easy to read, share, or publish later.

Running and testing the factory  Run the script and give it a topic that's actually covered by your sources folder — for example, if you  saved a few articles about chess, try "the history of chess." Watch the terminal as each agent's stage  runs in turn, and check that the saved file reads like a coherent, grounded post. Troubleshooting  ● The researcher comes back empty — check your sources folder actually has files in it and  that ingestion ran.

● The writer or editor invent facts that weren't in your sources — tighten the researcher's  instructions to report only what it retrieved, and the writer's instructions to use only the  facts it was given. ● Errors mentioning the model or provider — check your API key and model name match what  your chosen provider expects. Level up: stretch goals

● Blend RAG with a live web search tool for topics your local sources don't cover. ● Add a fourth "fact-checker" agent that cross-checks the writer's draft against the retrieved  passages before the editor sees it. ● Try a concurrent orchestration instead: have two writer agents draft different angles, and let  the editor pick the stronger one. ● Add a human-in-the-loop approval step so you review the draft before it's saved. Google ADK vs. Microsoft Agent Framework  Both are free, open source, and well-suited to learning agentic AI.

Here's how they compare, based  on what you used in this guide:   Google ADK Microsoft Agent Framework  Maintainer Google Microsoft  License Apache 2.0 MIT  Primary language Python (also Java, Go) Python and .NET  Core idea One Agent class, plain-function tools One Agent class, plain-function tools  Multi-agent style Sub-agents in a hierarchy  Named orchestration patterns:  sequential, concurrent, handoff, group  chat  Model access Gemini-first; other free providers via the optional LiteLLM connector Native connectors for Gemini and others; any OpenAI-compatible free provider works directly  Built-in dev UI adk web (stable) DevUI (preview)  Best fit for Learning core agent and tool concepts quickly, Gemini ecosystem Learning multiple named multi-agent orchestration patterns  Glossary  Agent — an AI system given a goal, a set of tools, and instructions, that decides on its own what to  do next to reach that goal.

Tool (function calling) — a regular function that an agent is allowed to call, such as a calculator or a  retrieval lookup. The framework reads the function's signature and docstring to know when and how  to use it. Instructions / system prompt — the standing guidance you give an agent about who it is, how it  should behave, and when to use each of its tools. Orchestration — the pattern that controls how multiple agents work together — for example, one  after another (sequential), all at once (concurrent), or handing off a conversation between them.

Embedding — a list of numbers that captures the meaning of a piece of text, so that texts with  similar meaning end up with similar numbers.

Vector database — a database built to store embeddings and quickly find the ones most similar to a  new piece of text. Retrieval-Augmented Generation (RAG) — a pattern where an agent first looks up relevant  information from a knowledge base, then uses that information to generate a grounded answer  instead of relying only on what the model already knows. Multi-agent workflow — a system made of several agents, each with a narrow job, that pass work to  one another to complete a larger task.
